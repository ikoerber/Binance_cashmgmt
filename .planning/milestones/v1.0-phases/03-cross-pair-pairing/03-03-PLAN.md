    **CRITICAL -- Secondary pair price sourcing for simulation (PairingPanel.jsx and PairingExistingTab.jsx):**

    The WebSocketContext provides `prices` as a map keyed by symbol (e.g., `prices['XRPBTC']`, `prices['BTCEUR']`). The backend streams price_update events for ALL known symbols, so XRPBTC and BTCEUR prices ARE available in the WebSocket `prices` map even when viewing the XRPEUR page. However, these prices may be null/undefined if the backend has not yet sent a price_update for that symbol.

    Implementation for simulation trigger:
    1. In both PairingPanel.jsx and PairingExistingTab.jsx, access the WebSocket prices map: `const { prices } = useWebSocket();` (import `useWebSocket` from `../contexts/WebSocketContext`).
    2. When triggering a simulation for a cross-pair pairing (one with `base_asset` set):
       - Read `xrpbtcPrice = prices['XRPBTC']` and `btceurPrice = prices['BTCEUR']` from the WebSocket prices map.
       - If BOTH are available (non-null): pass them as string values to `simulatePairing(userId, pairingId, marketPrice, feePct, feeBufferPct, null, xrpbtcPrice, btceurPrice)`. The API client converts to Decimal strings for transport.
       - If EITHER is null/undefined: call `simulatePairing()` WITHOUT the secondary prices (omit both params). The backend returns the simulation without `dual_route_comparison`. The SimulationModal simply does not render the dual-route section -- this is graceful degradation, not an error. No error toast needed.
    3. When triggering a simulation for a single-pair pairing (no `base_asset`): omit these params entirely (existing behavior).

    This approach ensures:
    - No additional REST calls needed (WebSocket already streams all pairs)
    - Graceful degradation: if secondary prices are not yet available, simulation works normally without dual-route
    - No silent omission bug: the dual-route section is explicitly conditional on data presence
