<feature>
  <name>Structured Error Classification + Enhanced Retry</name>
  <files>backend/app/utils/retry.py, backend/tests/test_retry.py</files>
  <behavior>
    Error classification (pure function, no I/O):

    1. `classify_error(exc) -> ErrorClassification`
       - Input: any Exception
       - Output: ErrorClassification(is_transient: bool, category: str, status_code: int|None, retry_after: float|None)
       - Categories: "rate_limit", "server_error", "timeout", "connection_error", "client_error", "unknown"

    2. Classification rules (from existing `_is_retryable` + enhancements):
       - BinanceAPIException with status_code 429 -> transient, category="rate_limit", extract Retry-After from response headers if available
       - BinanceAPIException with status_code >= 500 -> transient, category="server_error"
       - BinanceAPIException with status_code 4xx (not 429) -> permanent, category="client_error"
       - requests.exceptions.Timeout -> transient, category="timeout"
       - requests.exceptions.ConnectionError -> transient, category="connection_error"
       - requests.exceptions.HTTPError with response.status_code 429 -> transient, category="rate_limit", extract Retry-After header
       - requests.exceptions.HTTPError with response.status_code >= 500 -> transient, category="server_error"
       - requests.exceptions.HTTPError with response.status_code 4xx (not 429) -> permanent, category="client_error"
       - All other exceptions -> permanent, category="unknown"

    3. `BinanceAPIError(Exception)` — structured error wrapper:
       - Attributes: message, original_exception, classification (ErrorClassification), attempts (int)
       - Raised by retry decorator after all retries exhausted OR on permanent error
       - str representation: f"{category}: {message} (attempts={attempts}, status={status_code})"

    4. Enhanced `retry_on_transient_error` decorator behavior:
       - On transient error: wait with exponential backoff (existing behavior), BUT if Retry-After header present on 429, use max(backoff, retry_after) as wait time
       - On permanent error: raise BinanceAPIError immediately (no retry)
       - After all retries exhausted: raise BinanceAPIError with attempts count
       - Logging: existing warning logs + add info log when using Retry-After header value

    Test cases (input -> expected):
    - BinanceAPIException(status_code=429) -> transient, rate_limit
    - BinanceAPIException(status_code=500) -> transient, server_error
    - BinanceAPIException(status_code=502) -> transient, server_error
    - BinanceAPIException(status_code=400) -> permanent, client_error
    - BinanceAPIException(status_code=401) -> permanent, client_error
    - BinanceAPIException(status_code=403) -> permanent, client_error
    - requests.exceptions.Timeout() -> transient, timeout
    - requests.exceptions.ConnectionError() -> transient, connection_error
    - HTTPError(response=Mock(status_code=429)) -> transient, rate_limit
    - HTTPError(response=Mock(status_code=503)) -> transient, server_error
    - HTTPError(response=Mock(status_code=400)) -> permanent, client_error
    - ValueError("bad input") -> permanent, unknown
    - Retry-After header "5" on 429 -> retry_after=5.0
    - 429 without Retry-After -> retry_after=None (use default backoff)
    - Decorator with max_retries=2: transient error 3 times -> raises BinanceAPIError(attempts=3)
    - Decorator: permanent error on first call -> raises BinanceAPIError(attempts=1), no retry
    - Decorator: transient then success -> returns result, no error raised
    - Decorator: 429 with Retry-After=10 and base_delay=1 -> waits at least 10s (not 1s)
  </behavior>
  <implementation>
    Enhance `backend/app/utils/retry.py`:

    1. Add `ErrorClassification` dataclass:
       ```python
       from dataclasses import dataclass
       from typing import Optional

       @dataclass
       class ErrorClassification:
           is_transient: bool
           category: str  # "rate_limit", "server_error", "timeout", "connection_error", "client_error", "unknown"
           status_code: Optional[int] = None
           retry_after: Optional[float] = None
       ```

    2. Add `BinanceAPIError(Exception)`:
       ```python
       class BinanceAPIError(Exception):
           def __init__(self, message, original_exception, classification, attempts):
               ...
       ```

    3. Replace `_is_retryable()` with `classify_error()`:
       - Keep the same isinstance checks
       - Add Retry-After extraction: for BinanceAPIException, check `exc.response.headers.get("Retry-After")` if response exists; for HTTPError, check `exc.response.headers.get("Retry-After")`
       - Return ErrorClassification instead of bool
       - Keep `_is_retryable()` as a thin backward-compat wrapper: `return classify_error(exc).is_transient`

    4. Enhance `retry_on_transient_error` decorator:
       - Use `classify_error()` instead of `_is_retryable()`
       - If classification has retry_after, use `max(computed_delay, retry_after)` as wait time
       - On permanent error: wrap in BinanceAPIError and raise immediately
       - After all retries: wrap in BinanceAPIError with attempts count
       - Log Retry-After usage at INFO level

    IMPORTANT: Keep the existing decorator signature and behavior for backward compatibility. All existing `@retry_on_transient_error()` usages must continue to work without changes.

    For tests, use unittest.mock to simulate BinanceAPIException and requests exceptions. Use `time.sleep` mocking to verify backoff timing without actual delays.
